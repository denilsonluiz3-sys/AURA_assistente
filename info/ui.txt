TAREFA: MIGRAÇÃO COMPLETA DA APARÊNCIA DA AURA

Tenho dois repositórios da AURA.

O objetivo é transportar para o repositório DESTINO toda a identidade visual, aparência e experiência de interface existente no repositório de REFERÊNCIA.

REPOSITÓRIO DESTINO

"https://github.com/denilsonluiz3-sys/AURA_assistente"

Este é o projeto que deve receber a aparência.

REPOSITÓRIO DE REFERÊNCIA

Use o repositório de referência fornecido pelo usuário anteriormente nesta conversa como FONTE DA APARÊNCIA.

Não assuma que os dois projetos possuem a mesma estrutura.

---

OBJETIVO PRINCIPAL

Quero que o "AURA_assistente" fique visualmente equivalente ao repositório de referência.

Não quero simplesmente copiar arquivos.

Quero migrar o DESIGN SYSTEM e todos os elementos visuais necessários, adaptando-os à arquitetura atual do "AURA_assistente".

A aparência da referência deve ser tratada como a fonte de verdade visual.

A arquitetura e as funcionalidades do "AURA_assistente" devem ser preservadas.

---

REGRA FUNDAMENTAL

NÃO ALTERE O CÓDIGO IMEDIATAMENTE.

Primeiro:

1. inspecione a referência;
2. inspecione o destino;
3. compare os dois;
4. descubra como a aparência foi implementada na referência;
5. descubra como a interface atual do destino funciona;
6. monte um mapa de migração;
7. só então implemente.

Não faça tentativa e erro visual através de vários patches.

FASE 3 — COMPARAÇÃO

Crie internamente uma matriz:

REFERÊNCIA → DESTINO

- comparar implementação;
- identificar diferença;
- adaptar o destino.

2. Existe somente na referência?

- se deve ser criado;
- onde deve ficar;

Mapear semanticamente.

"AuraSurface" na referência

pode corresponder a outro recurso no destino.

Não duplique recursos sem necessidade.

FASE 8 — COMPATIBILIDADE MAUI

O projeto utiliza .NET MAUI.

Antes de introduzir qualquer propriedade XAML:

verifique se ela é realmente suportada pelo controle e pela versão do MAUI usada pelo destino.

Não copie propriedades visualmente atraentes que não existem ou não funcionam no Android.

Já houve problemas anteriores no projeto com propriedades XAML incompatíveis.

Portanto:

NÃO faça:

"copiar propriedade → compilar → descobrir erro → adicionar patch → outro erro".

Faça:

"identificar propriedade → verificar compatibilidade → implementar → compilar".

---

FASE 9 — NÃO DESTRUIR O ESTADO FUNCIONAL

Antes de alterações importantes:

- preserve o estado atual;
- trabalhe de forma incremental;
- mantenha alterações relacionadas agrupadas;
- não faça mudanças indiscriminadas.

Se algo quebrar:

1. pare;
2. descubra a causa;
3. compare com o estado anterior;
4. corrija a causa;
5. valide novamente.

Não empilhe patches sobre uma implementação já quebrada.

---

Procure inconsistências como:

- uma página com outro background;
- botão diferente;
- fonte diferente;
- padding diferente;
- CornerRadius diferente;
- texto com outra hierarquia;
- ícone incompatível;

- estilos duplicados.

Quando encontrar uma inconsistência causada pelo Design System, corrija o sistema global em vez de criar uma exceção local.
